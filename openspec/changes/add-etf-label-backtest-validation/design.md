## Context

当前系统已经记录 ETF 短线信号，并有真实前瞻验证任务：信号生成后等待未来 1/3/5/10 个交易日，再补齐实际收益和回撤。这条链路最干净，但上线时间短时会出现 `completed_outcomes=0`，导致用户只能看到“规则标签”，看不到足够历史样本。

短线 ETF 标签需要两类证据共同存在：

- 历史回放验证：用当前规则在过去每天重放，快速形成样本，回答“类似标签过去表现如何”。
- 真实前瞻验证：只用系统上线后真实产生的标签，回答“上线后的标签是否继续有效”。

本设计只增加历史回放验证和展示，不改变实时排序、盘中盯盘、邮件提醒或组合权重。

## Goals / Non-Goals

**Goals:**

- 对 ETF `买入观察状态 + 今日买点状态` 做历史回放验证。
- 严格避免未来函数：回放日只能使用当日及以前的数据生成标签。
- 统计 1/3/5/10 个交易日后的收益、胜率、最大不利回撤、最大有利波动和样本数。
- 在 `/short-term` 展示历史回放证据和真实前瞻证据，并明确两者区别。
- 样本不足、样本偏短、数据覆盖不足时，必须显示谨慎状态。

**Non-Goals:**

- 不用历史回放结果自动改当前标签、分数、组合权重或邮件提醒。
- 不训练模型，不引入强化学习或预测模型。
- 不连接券商，不自动交易。
- 不把历史回放包装成“保证未来有效”。
- 不替代真实前瞻验证。

## Decisions

### 1. 历史回放和真实前瞻分开存储或至少分开模式

历史回放结果必须带 `validation_mode=historical_replay`；现有前瞻结果继续使用 `forward_live` 或等价口径。

原因：两者可信含义不同。历史回放样本多，但可能有幸存者偏差和规则版本偏差；真实前瞻样本少，但更接近真实使用过程。

备选方案：直接把历史回放写入现有前瞻结果。拒绝，因为会让用户误以为这些样本都是系统真实运行后产生的。

### 2. 回放引擎复用当前标签规则，但必须传入历史截止日

回放过程对每个 `replay_date` 调用同一套标签计算逻辑，但所有行情、日线、成交额、均线、回撤和风险指标都必须截止到 `replay_date`。

原因：这能测试“当前规则如果过去就存在，会打出什么标签”，同时最大限度降低实现分叉。

备选方案：直接复用历史缓存 signal items。拒绝作为唯一方案，因为历史缓存只从系统上线后开始，无法快速补足样本。

### 3. 结果按标签组合聚合，同时保留样本明细

聚合维度至少包含：

- `observation_label`
- `entry_timing_label`
- `horizon_days`
- `rule_version`
- `asset_type=etf`

明细样本保留 asset code、replay date、entry close、future close、future return、max adverse excursion、max favorable excursion、exclusion reason。

原因：用户关心“健康回踩过去是否比冲高别追更稳”，而排查问题时需要回到具体样本。

### 4. 置信度采用保守门槛

默认置信状态：

- `< 30` 个完成样本：`insufficient`
- `30-99` 个完成样本：`limited`
- `>= 100` 个完成样本：`sufficient`

如果最近验证时间过旧或数据覆盖率不足，即使样本数足够也要降级。

原因：短线标签容易受市场阶段影响，样本不足时不能用“历史可靠”措辞。

### 5. UI 同屏展示历史回放和真实前瞻

标签可信度区域分成两块：

- `历史回放`：历史样本证据，带样本数和偏差提示。
- `真实前瞻`：系统上线后的真实跟踪结果，样本不足时显示等待。

原因：用户现在的问题是“等到 7 月是不是过时”，历史回放解决及时性，真实前瞻保留长期校验。

### 6. 使用协调者 + 并行智能体执行

本变更实施时采用一个主协调者和多个并行智能体的模式。

主协调者职责：

- 明确每轮目标、修改边界和验收标准。
- 给每个并行智能体分配互不重叠的任务。
- 审核每个智能体带回的报告和代码差异。
- 发现问题后给出反馈，并继续分配下一轮修正任务。
- 最终整合变更，统一跑测试、检查 UI、提交和部署。

并行智能体建议角色：

- `研究智能体`，建议模型 `5.5high` 或 `5.4xhigh`：审查成熟项目做法、验证指标定义、无未来函数风险、样本门槛和统计口径，输出风险清单与推荐实现口径。
- `后端智能体`，建议模型 `5.3codex`：实现迁移、历史回放引擎、聚合统计、API 和后端测试，不改前端。
- `前端智能体`，建议模型 `5.3codex`：实现 `/short-term` 标签证据展示、空状态、双轨说明和构建验证，不改后端业务逻辑。
- `审核智能体`，建议模型 `5.5high` 或 `5.4xhigh`：做代码审查、金融语义审查、性能风险审查和截图/接口验收，输出阻塞项和建议。

每个智能体必须行动、迭代并带回深入报告。报告至少包含：已完成内容、修改文件、关键设计取舍、验证结果、发现的问题、需要协调者决策的事项。

## Risks / Trade-offs

- [Risk] 幸存者偏差：当前 ETF 池可能不包含过去已经退市或长期缺数据的 ETF。  
  Mitigation: UI 明确标注“基于当前可用 ETF 历史数据回放”，并记录 universe 版本和数据覆盖率。

- [Risk] 规则版本偏差：用今天的规则回放过去，不能证明当时真实系统会这样运行。  
  Mitigation: 每次回放记录 `rule_version`，并和真实前瞻验证分开展示。

- [Risk] 计算量增加：全 ETF、长时间窗口、多周期回放会较慢。  
  Mitigation: 默认只回放近 180 或 365 个交易日，使用批量读取日线数据，任务在后台运行，不阻塞页面。

- [Risk] 用户误把历史胜率当成买入保证。  
  Mitigation: 文案使用“历史回放证据 / 样本表现”，禁止“必涨、稳赢、推荐买入”等措辞。

- [Risk] 日线和盘中口径混淆。  
  Mitigation: 历史回放第一版只使用日线收盘价，不参与盘中邮件触发。

## Migration Plan

1. 新增或扩展验证结果存储，确保历史回放和真实前瞻可区分。
2. 增加历史回放任务，默认参数为 ETF、近 180/365 个交易日、1/3/5/10 日窗口。
3. 增加 API 返回最新历史回放聚合结果。
4. 前端在 `/short-term` 标签证据区域展示双轨验证。
5. 部署后先手动运行一次历史回放任务，再观察样本覆盖率。

Rollback 策略：保留新表或新字段但隐藏前端入口；实时排序、追踪、邮件和组合链路不依赖该结果，可以独立回滚 UI/API 调用。
